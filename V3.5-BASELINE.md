# V3.5 Baseline Assessment

## Project state
- Repository root: `Payment-Platform-V3.4.1-Windows-Local-Ready`
- Package version: `3.4.1`
- Workspace layout: monorepo with `apps/api`, `apps/web`, `packages/contracts`.
- Current implementation still targets a Fastify API + React web console with the existing V1 API surface under `/v1/*`.

## Database state
- Migration runner exists in `apps/api/src/scripts/migrate.ts` and scans `database/migrations/*.sql` in lexical order.
- The schema is currently composed from legacy migrations `000` through `010`.
- The payment schema already includes core payment tables, but the project still relies on runtime compatibility for newer columns that were added in later migrations.

## Current APIs
The current runtime exposes the following primary API families, all under `/v1/`:
- Authentication: `/v1/auth/login`, `/v1/auth/mfa/verify`, `/v1/auth/me`, `/v1/auth/logout`
- Payments: `/v1/payment-sessions`, `/v1/payment-sessions/:id/pay`, `/v1/payments`, `/v1/refunds`
- Customers: `/v1/customers`
- Payment links: `/v1/payment-links`
- Financial: `/v1/balance`, `/v1/settlements`, `/v1/payouts`, `/v1/reconciliation/*`
- Subscriptions: `/v1/products`, `/v1/prices`, `/v1/subscriptions`
- Integration and developer surfaces: `/v1/api-keys`, `/v1/webhook-endpoints`, `/v1/webhook-deliveries`, `/v1/integrations/zoho-books/*`

## Known issues observed
1. The primary runtime failure reported by the implementation is the schema mismatch around payment tables: `Unknown column 'payment_method_id' in 'field list'`.
2. The code path in `apps/api/src/application/payments/payment-service.ts` inserts `payment_method_id` into payment tables, but the schema compatibility is not guaranteed by a dedicated V3.5 migration.
3. The API test command currently returns no test files and exits with code 1:
   - `npm test` → `No test files found, exiting with code 1`
4. The API build command currently compiles successfully with TypeScript:
   - `npm run build -w apps/api` exited successfully.
5. The local dev commands currently show exit code 1 in the terminal state, which means the Windows local runtime is still not fully verified end-to-end.

## What has been fixed in this baseline step
- Introduced a formal V3.5 compatibility migration to harden payment schema compatibility.
- Added a dedicated schema remediation path so old / partially upgraded databases are given the missing payment columns before runtime execution.
- Recorded the current state in this baseline document so Phase 1 work starts from a documented boundary condition.

## What remains unresolved
- The repo still has no real V3.5 test suite under `tests/` that can prove the new lifecycle end-to-end.
- The remaining V3.5 Phase 1 architecture work still needs to be implemented across identity, subscriptions, invoices, ledger, outbox, providers, and books integration.
- The Windows local dev environment still needs a full end-to-end verification path before calling the platform ready.
