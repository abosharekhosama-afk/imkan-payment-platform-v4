# تقرير شامل — حالة مشروع إمكان للمدفوعات (V4)

**التاريخ:** 13 أغسطس 2026  
**الإصدار:** Payment Platform V3.4.1  
**الجمهور:** الإدارة والمنتج والتشغيل  
**الحكم المختصر:** المنصة جاهزة كـ **طبقة تحصيل وتشغيل** عبر Stripe Live في حساب المنصة، بعد إغلاق قائمة التشغيل. **ليست** جاهزة كمنصة صرف تلقائي إلى IBAN كل شركة، ولا كبوابة فلسطين حية.

تقرير اليوم التنفيذي الأقصر: [`2026-08-13-daily.md`](./2026-08-13-daily.md)

---

## 1. ما هو المنتج اليوم

إمكان منصة متعددة التجار (multi-merchant) لـ:

- تسجيل الشركات والتحقق منها (KYB)
- إنشاء روابط دفع وصفحات Checkout
- تحصيل البطاقات عبر مزود خارجي (Stripe، وPayTabs في المسار الرملي / الحي المشروط)
- تسجيل الرسوم والصافي وكشوف الحساب
- تسجيل نية الصرف إلى IBAN بموافقة مزدوجة

**نموذج المال الحالي (مهم للإدارة):**

```
العميل يدفع
  → Stripe أو PayTabs (غالباً حساب المنصة المشترك)
  → إمكان تسجّل العملية والرسوم والصافي
  → تحويل التاجر يتم خارج إمكان (لوحة Stripe أو حوالة يدوية)
  → إمكان تسجّل «مدفوع» بعد دليل التحويل
```

هذا نموذج **Facilitator / حساب مجمّع**، وليس Stripe Connect ولا تسوية مباشرة من البنك إلى IBAN التاجر.

## 2. الحكم على المرحلة

| السؤال | الجواب |
|---|---|
| هل النظام يعمل محلياً / تجريبياً؟ | نعم |
| هل يمكن إطلاق إنتاج محدود لتحصيل البطاقات؟ | نعم، بعد Redis والبريد وStripe الحي وWebhook والجلسات |
| هل المال يصل تلقائياً لحساب الشركة البنكي؟ | لا |
| هل فلسطين (ILS) جاهزة للتحصيل الحي؟ | لا — بانتظار عقد ووثائق API |
| هل الخليج (PayTabs الحي) جاهز بضغطة زر؟ | لا — يحتاج علماً تشغيلياً وعقداً |
| هل بوابة «Production Ready» الرسمية مُمرَّرة؟ | لا — ما زالت **NOT PASSED** لأسباب PCI والصرف الحي والاختبارات التشغيلية |

## 3. المعمارية التقنية (باختصار)

| الطبقة | الاختيار |
|---|---|
| الواجهة | React / Vite — لوحة تاجر + لوحة منصة + Checkout عام |
| الـ API | Node / Fastify — المسار العام `/api/v1` على PostgreSQL |
| قاعدة البيانات | PostgreSQL (Neon أو مدار) — مصدر الحقيقة لـ V4 |
| الجلسات | كوكيز HttpOnly في الإنتاج (موصى به) |
| الطوابير / البريد / الويب هوك الصادر | Outbox داخل عملية الـ API |
| المزوّدون | طبقة Adapter + Router (sandbox / stripe / paytabs / هيكل BOP) |
| الأموال في الكود | وحدات صغرى صحيحة (`NUMERIC`) مع عملة ISO — لا أرقام عشرية عائمة |

مسار MySQL القديم موجود تاريخياً **ولا يُعد عقد V4**. الإنتاج يجب أن يستخدم PostgreSQL و`/api/v1` فقط.

## 4. حالة الوحدات بالتفصيل

### 4.1 الهوية والشركات والأدوار

| القدرة | الحالة | ملاحظات |
|---|---|---|
| تسجيل / دخول / تحقق البريد | مكتمل | يحتاج SMTP حقيقي في الإنتاج |
| MFA وتحقق إضافي (step-up) للعمليات الحساسة | مكتمل | تفعيل حساب بنكي، استرداد، مفاتيح API، صرف |
| دعوات الفريق وقبول الدعوة | مكتمل بعد إصلاح Idempotency | المدعو ينشئ اسماً وكلمة مرور |
| RBAC وصلاحيات وعزل الشركات | مكتمل ومختبر | أدوار تاجر + أدوار منصة |
| أدوار مخصصة | مكتمل مع حراسة التصعيد | |

**ناقص لاحقاً:** ربط KMS سحابي للأسرار بدل متغيرات البيئة فقط.

### 4.2 التحقق من الشركة (KYB) والمستندات

| القدرة | الحالة |
|---|---|
| ملف الشركة، النشاط، الأشخاص | مكتمل |
| رفع مستندات | مكتمل (تخزين كائنات) |
| إرسال KYB ومراجعة المنصة في الواجهة | مكتمل |
| منع إنشاء روابط الدفع قبل حالة KYB مسموحة | مكتمل على الخادم (`REQUIRE_KYB_FOR_PAYMENTS`) |

حالات KYB المعتمدة للسماح بالمال عند تفعيل البوابة: مُرسل / قيد المراجعة / مقبول (حسب إعداد البوابة). الواجهة الأمامية **لا يمكنها تجاوز** هذا الشرط.

**ناقص لاحقاً:** مزود تحقق خارجي حقيقي (اليوم المراجعة داخلية/يدوية).

### 4.3 الحساب البنكي (IBAN)

| القدرة | الحالة |
|---|---|
| إضافة IBAN مشفّر مع إخفاء الرقم | مكتمل |
| منع التكرار ببصمة غير عكسية | مكتمل |
| قائمة مراجعة المنصة `/platform/bank-accounts` | مكتمل (13 أغسطس) |
| اعتماد / رفض / تفعيل من المنصة أو التاجر | مكتمل |
| اختبارات دورة الحياة + تفعيل الأدمن | 12/12 ناجحة |

التفعيل يعني: الحساب صالح **لتسجيل الصرف في إمكان**. لا يعني أن البنك استلم حوالة.

### 4.4 التحصيل وروابط الدفع وCheckout

| القدرة | الحالة |
|---|---|
| روابط دفع (لمرة واحدة افتراضياً) | مكتمل |
| Checkout عام + Stripe Elements | مكتمل |
| مزامنة العودة من Stripe + Webhook | مكتمل |
| منع إعادة استخدام الرابط بعد النجاح | مكتمل |
| إشعار أنظمة خارجية (كتب / فواتير) عبر Webhook صادر | مكتمل تقنياً |

**ناقص للإنتاج:** مفاتيح Stripe الحية، سر Webhook، عنوان عام HTTPS، واختبار دفعة حية واحدة.

### 4.5 الرسوم والدفتر والتسويات والتقارير

| القدرة | الحالة |
|---|---|
| تقسيم الرسوم لكل دفعة (منصة / مزود / صافي) | مكتمل في هذه الدورة |
| كشف حساب + CSV | مكتمل |
| دفتر قيد مزدوج وأرصدة | مكتمل كطبقة داخلية |
| تسوية (مسودة → إغلاق → إلغاء) | مكتمل داخلياً |
| شاشات المحفظة والتقارير | مكتمل (لم تعد «قريباً») |
| احتياطي دوّار (rolling reserve) | مؤجّل (قيمة 0) |
| تحويل عملات (FX) | مؤجّل — عملة واحدة لكل تسوية |
| ضرائب | مؤجّل لنظام الحسابات |

### 4.6 الصرف (Payout)

| القدرة | الحالة |
|---|---|
| إنشاء صرف من صافي التسوية | مكتمل |
| إرسال → اعتماد بمنصة + دليل خارجي → تعليم كمدفوع | مكتمل |
| سكة يدوية مدققة (الافتراضية) | مكتمل |
| استدعاء بنك / تحويل API إلى IBAN | **غير موجود** |
| Stripe Connect | **خارج النطاق** |

`mark-paid` = «التحويل تم خارج النظام ولدينا مرجع». في غير الإنتاج يمكن كسر الزجاج للاختبار فقط.

### 4.7 المزوّدون حسب السوق

| السوق | التحصيل | الحالة |
|---|---|---|
| دولي / بطاقات عبر Stripe | Stripe (اختبار + حي مشروط بـ `STRIPE_ALLOW_LIVE`) | جاهز تقنياً بعد المفاتيح |
| الخليج (سعودي، إماراتي، …) | PayTabs | رملي مختبَر؛ الحي يحتاج علماً وعقداً |
| فلسطين (ILS) | بنك فلسطين / جوال / غيرها | بحث + حزم مراسلة جاهزة؛ **لا API عامة**؛ المحول هيكل يرفض العمليات المالية |
| Sandbox الداخلي | محاكاة | للاختبار فقط — ممنوع كسكة إنتاج |

التوجيه الإقليمي في الكود: الشيكل → محول فلسطين؛ عملات الخليج → PayTabs؛ دولار/يورو → Stripe. إن لم تربط الشركة حساب مزود خاصاً بها، المال يذهب لحساب المنصة المشترك.

### 4.8 الفوترة (اشتراكات / فواتير / عملاء)

موجودة في اللوحة والـ API على المسار الرملي. التجديد الحي الكامل ورمز البطاقة الحقيقي للفوترة المتكررة **غير مغلقين كإنتاج فوترة**. الإطلاق الأول يجب أن يركز على **روابط الدفع لمرة واحدة** لا على الاشتراكات الحية.

### 4.9 الأمان والتشغيل

| القدرة | الحالة |
|---|---|
| عزل المستأجرين | مختبَر |
| عدم تخزين PAN/CVV في إمكان | سياسة ثابتة (Stripe/PayTabs يستضيفان الحقول) |
| حد معدل موزّع عبر Redis | جاهز معمارياً — إلزامي في الإنتاج |
| نسخ احتياطي محلي | سكربتات موجودة؛ النسخ خارج الموقع غير مغلق |
| مراقبة أساسية (`/health/ready`, metrics) | موجودة |
| اختبار اختراق رسمي | غير منفَّذ |
| اختبار حمل | غير منفَّذ |
| شهادة PCI SAQ | غير منفَّذة (DEC-011) |

### 4.10 الواجهة (أغسطس 2026)

- لوحة تاجر + لوحة منصة + Checkout
- تحسين موبايل: هيدر رفيع، قائمة مسطحة بأيقونات، شيمر تحميل
- نصوص أدوار وحالات مفهومة للمستخدم
- اللغة والمظهر من صفحة المظهر وليس من أعلى الشاشة

## 5. مسار المال — ماذا نقول للتجار وللإدارة

### ما يحدث اليوم إذا دفع عميل بطاقة

1. المال يدخل **حساب Stripe (أو PayTabs) الخاص بالمنصة** في الحالة الافتراضية.
2. إمكان تعرض للشركة العملية والرسوم والصافي.
3. تحويل الرصيد إلى بنك الشركة يتم **من لوحة Stripe** أو بحوالة تشغيلية.
4. بعد التحويل، المالية تسجّل الصرف في إمكان مع رقم الحوالة.

### ما يطلبه المنتج المستهدف (Zoho-like)

تحصيل إقليمي → IBAN كل شركة مباشرة، مع شفافية الرسوم.

للوصول إلى ذلك يلزم واحد أو أكثر من:

1. **MID لكل تاجر** لدى بنك فلسطين / جوال (فلسطين)
2. **حساب PayTabs لكل شركة** أو تسوية PayTabs واضحة (الخليج)
3. **Stripe Connect** لاحقاً للخليج/الدولي — غير مبني

حتى ذلك الحين، التسويق يجب أن يقول: **تحصيل عبر إمكان، والتسوية البنكية عبر تشغيل المنصة / Stripe**، لا «يصلك المبلغ فوراً على الآيبان».

## 6. ما نحتاجه للدخول في الإنتاج (المرحلة أ)

هذه قائمة تشغيل لا ميزات برمجية كبيرة:

1. رفع الكود المصدري (بدون اعتماد `dist` كمصدر)
2. PostgreSQL إنتاجي + ترحيلات
3. Redis + تخزين حد المعدل على Redis
4. بريد حقيقي (SMTP أو Brevo) والتحقق من البريد
5. جلسات كوكيز وبناء الواجهة بنفس الإعداد
6. مفاتيح Stripe الحية + Webhook عام
7. تفعيل `STRIPE_ENV=live` و`STRIPE_ALLOW_LIVE=true`
8. إنشاء مالك المنصة ومسارات Stripe
9. `REQUIRE_KYB_FOR_PAYMENTS=true`
10. دفعة تجريبية حية: نجاح → انتهاء الرابط → قيد في الكشف
11. دليل مكتوب: من يحوّل من Stripe، وكيف يُعبأ تعليم المدفوع في إمكان

بعد ذلك يمكن فتح **تجار محدودين** على التحصيل فقط.

## 7. ما نحتاجه لاحقاً (خريطة طريق)

### المرحلة ب — تشغيل مالي منضبط (أسابيع)

- دليل صرف يومي/أسبوعي بين المالية وإمكان
- تدريب المنصة على KYB ومراجعة IBAN
- نسخ احتياطي خارج الموقع وجدولة
- مراجعة أمنية خارجية (اختبار اختراق)
- ملف PCI SAQ المناسب لعنصر Stripe المستضاف

### المرحلة ج — الخليج الحي (عند وجود تجار خليج)

- عقد PayTabs
- `PAYTABS_ALLOW_LIVE=true`
- Webhook PayTabs عام
- حساب بوابة لكل شركة إن لزم (لا حساب منصة فقط)
- قائمة تشغيل الخليج الموجودة في الوثائق الداخلية

### المرحلة د — فلسطين (موقف على الشركاء)

- إرسال حزم المراسلة الجاهزة لبنك فلسطين ثم العربي ثم جوال/بال باي
- استلام وثائق API الخاصة وبيانات التجربة
- بناء المحول الحقيقي (اليوم يرفض عمليات المال عمداً)
- نموذج MID لكل تاجر — لا حساب منصة مجمّع إن رفض البنك ذلك

### المرحلة هـ — صرف مباشر / Connect (منتج لاحق)

- قرار تجاري: Connect أم تسوية مزود لكل تاجر أم استمرار الحساب المجمّع
- بناء السكة (غير موجودة اليوم)
- لا يُعلن للمستخدم أنها موجودة قبل العقد والكود

### المرحلة و — الحسابات والكتب (Zoho / نظام داخلي)

- موصول جزئياً تاريخياً؛ عامل كتب V4 غير مكتمل (DEC-016)
- يمكن الاعتماد مؤقتاً على Webhook الصادر لأنظمة الفواتير

### مؤجّل بقرار

- تحويل العملات داخل المنصة
- الاحتياطي الدوّار
- الضرائب داخل نواة المدفوعات
- الفوترة المتكررة الحية الكاملة

## 8. المخاطر التي يجب أن تعرفها الإدارة

| المخاطر | الأثر | التخفيف |
|---|---|---|
| توقع التاجر أن IBAN يعني تحويلاً تلقائياً | شكاوى وثقة | نصوص واضحة في اللوحة والعقود |
| المال في حساب Stripe المنصة | تركيز مخاطر وامتثال | سياسة تسوية مكتوبة؛ Connect لاحقاً |
| إطلاق بلا Redis/بريد/Webhook | دفع حي وجلسات وبريد تنكسر | لا إطلاق قبل قائمة المرحلة أ |
| فلسطين بلا عقد | لا تحصيل ILS حي | المراسلة أولاً |
| PAN على خوادمنا | خروج عن نطاق PCI | ممنوع — السياسة الحالية صحيحة |
| وثائق قديمة تقول «التقارير غير منفذة» | لبس داخلي | التقارير والمحفظة نُفِّذتا في هذه الدورة |

بوابة الإنتاج الرسمية في الوثائق ما زالت **غير مُمرَّرة**. ذلك لا يمنع إطلاق **شريحة تحصيل محدودة** إذا وافقت الإدارة صراحة على النموذج المجمّع وعلى قائمة التشغيل، مع عدم استخدام عبارة «Production Ready» الشاملة.

## 9. توصية القرار

**يُوصى بالموافقة على إطلاق إنتاج مرحلي (تحصيل Stripe + تشغيل يدوي للتسوية البنكية)** بعد إغلاق المرحلة أ.

**لا يُوصى** بالإعلان عن:

- صرف فوري إلى IBAN
- جاهزية فلسطين الحية
- جاهزية PayTabs الحية قبل العقد والعلم التشغيلي
- اكتمال PCI أو اختبار الاختراق

العمل الهندسي لهذه الدورة (رسوم، كشف، مراجعة بنك، تجربة موبايل، اختبارات KYB/بنك، إصلاح الدعوة) **مكتمل كمنتج برمجي لهذه الشريحة**. ما تبقّى للدخول في الإنتاج هو **تشغيل وعقود وشريك فلسطين**، لا إعادة بناء المنصة.
