# Implementation Plan v2 — Merchant Console + Payments + Refunds + Payment Links + Hosted Checkout

## Current repository baseline

The supplied repository is a small but connected TypeScript payment core. The main production-facing files are:

- `apps/api/src/interfaces/http/routes.ts` — HTTP surface and authentication.
- `apps/api/src/application/payments/service.ts` — payment/refund/link application logic.
- `apps/api/src/infrastructure/providers/sandbox.ts` — simulated provider.
- `apps/api/src/domain/ledger/ledger.ts` — ledger invariant helper.
- `apps/api/src/domain/payments/state.ts` — payment transition rules.
- `database/migrations/001_core.sql` — core payment/ledger schema.
- `database/migrations/002_v1_1_core.sql` — payment methods, links, webhooks.
- `database/migrations/003_production_foundation.sql` — API keys, RBAC foundation, webhook attempts.
- `apps/web/src/main.tsx` — current single-file merchant console.
- `apps/web/src/style.css` — current console styling.

## Phase 1 implemented in this package

### Backend

- Added a real `GET /v1/refunds` collection endpoint.
- Upgraded `GET /v1/payments` with search/status/currency/limit/offset parameters.
- Upgraded customer listing with search and pagination.
- Added payment detail aggregation: payment + attempts + refunds + ledger + outbox events.
- Validated merchant ownership when creating payment links.
- Added public payment-link lookup validation for status and expiry.
- Added public sandbox checkout payment endpoint: `POST /checkout/public/:token/pay`.
- Kept raw card data out of the application; the sandbox checkout intentionally does not collect PAN/CVV.
- Kept API-key creation explicitly in test namespace (`pk_test_`).

### Merchant Console

Replaced the generic `DataPage` renderer with real module workflows for:

- Dashboard
- Payments
- Payment details drawer
- Refund creation from payment details
- Customers
- Customer creation
- Payment Links
- Payment-link creation/copy/cancel
- Refunds
- Balances
- API keys
- Webhooks
- Audit log

### Public Checkout

Added a responsive public checkout route at:

`/checkout/public/:token`

The current checkout is sandbox-only. It completes a sandbox payment without collecting card details. It must be replaced by processor-hosted tokenization before any real-money deployment.

## Files that remain intentionally experimental

### `apps/api/src/infrastructure/providers/sandbox.ts`

Keep this file for automated tests and local demos. It must not be presented as a real processor.

Replace the provider construction later with:

```text
PaymentProvider
├── SandboxProvider
└── RealProcessorAdapter
```

### `POST /v1/payment-method-sessions`

This currently returns a generated `client_secret`. It is a placeholder for processor-hosted tokenization.

### `POST /v1/payment-methods`

This endpoint accepts a provider token, which is acceptable as an internal sandbox abstraction, but the token must be generated by the real processor in production.

## Phase 3 — Hosted Checkout with real processor tokenization

- `POST /v1/checkout/sessions`

- `POST /v1/checkout/sessions/:id/confirm`

### New tables

`004_checkout.sql` should add:

- `checkout_sessions`
- `checkout_attempts`
- optional `checkout_customer_fields`

Recommended checkout session fields:

- id
- tenant_id
- merchant_id
- payment_session_id
- public_token
- status
- locale
- success_url
- cancel_url
- expires_at
- created_at
- updated_at

### Security

The browser must never submit raw PAN/CVV to this application. Use processor-hosted fields/elements or redirect checkout.

## Phase 4 — Webhook delivery

Create:

- `apps/api/src/application/webhooks/service.ts`
- `apps/api/src/workers/outbox-worker.ts`
- `apps/api/src/workers/webhook-worker.ts`
- `apps/api/src/infrastructure/webhooks/signer.ts`

Flow:

```text
Domain event
  -> outbox_events
  -> worker claims event
  -> webhook delivery row
  -> signed HTTP request
  -> attempt row
  -> success / retry / DLQ
```

Required states:

`PENDING -> DELIVERING -> DELIVERED`

or:

`PENDING -> RETRYING -> DLQ`

New tables:

- `reconciliation_runs`
- `reconciliation_items`
- `reconciliation_exceptions`

Matching hierarchy:

1. provider transaction ID
2. provider reference
3. amount + currency + timestamp window
4. explicit manual match

Never silently auto-adjust money because a match failed.

## What should be deleted/replaced later

Do not delete the sandbox provider immediately. Replace its usage behind a provider interface.

Replace these patterns:

- `new PaymentService()` in `routes.ts` with dependency injection.
- SQL directly inside HTTP routes with application/repository services.
- `DataPage`-style dynamic tables with typed module tables.
- development `X-Tenant-ID` fallback with authenticated tenant context.
- random `client_secret` generation with real provider tokenization.
- direct `SandboxProvider` dependency with `PaymentProvider` port.

## Acceptance criteria for the current phase

- Merchant can list/search payments.
- Merchant can open a payment and inspect attempts/refunds/ledger/events.
- Merchant can create a partial or full refund with idempotency.
- Merchant can create/cancel/copy a payment link.
- Public user can open a payment link.
- Public user can complete a sandbox checkout.
- Refunds have their own collection page.
- API keys can be created/revoked.
- Webhook endpoints can be registered and outbox events inspected.
- Dashboard and balances use live database values.

## Important production boundary

The current package is still sandbox software. The public checkout is deliberately not a card form. Real-money readiness begins only after a licensed/PCI-compliant processor is integrated, processor-hosted tokenization is used, webhook delivery is reliable, settlements/payouts/reconciliation exist, and security/compliance testing is completed.
